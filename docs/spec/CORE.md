# SPEC-CORE — JSONL パーサとインデクサ（基本仕様書）

担当 Issue: #2（パーサ・インデクサ）/ #4（実測値照合レポート）/ #28（ログソース抽象化とセッション発見）/ #41（worktree セッションの本体統合）/ #49（同一プロジェクトの Claude / Codex 表示統合）

## ゴール

セッション JSONL（Claude Code は 1 ファイル最大 69MB・1 行最大 1.3MB）を全読み込みせずに解析し、セッション横断で集計可能な軽量インデックスを構築する。

セッションの**発見と識別**はログソース抽象（Issue #28）の背後に置き、`~/.claude/projects/<project>/<session>.jsonl` という Claude 固有の配置前提をサーバ本体から解消する。将来の Codex CLI 対応（#29 以降）は、ソースを 1 つ追加するだけで viewer 側を変更せずに済む構造を保つ。

## できること

- セッション JSONL を走査し、メッセージ・ツール呼び出し・トークン使用量などの**軽量メタだけ**を持つインデックスを作る（全文はメモリに載せない。詳細表示時に該当行だけを読み出す）
- 2 回目以降は**追記された差分だけ**を解析する（進行中セッションの追従が速い）
- **壊れた行があっても全体は落ちない**（スキップして件数を報告する）
- モデル別トークン合計・ツール別呼び出し回数・期間・タイトルなどのセッション要約を出す

## ログソース抽象とセッション発見（Issue #28）

### できること

- **ログソースの抽象境界を導入する。** 「配下のセッションを発見し、グループ（プロジェクト相当）と ID を与える」責務をソースごとの実装に分離する。サーバ本体（store / API / 集計）はソースが返す一覧だけを見る
- **Claude 単独利用時の挙動は一切変わらない。** セッション ID（ファイル名から拡張子を除いたもの）・プロジェクト ID・API レスポンス・集計値は従来と同一（既存テストを変更せずに green のまま）
- **Codex の日付階層からセッションを発見できる。** `~/.codex/sessions/YYYY/MM/DD/rollout-<ISO日時>-<UUID>.jsonl` を再帰探索し、rollout ファイル**単独**で発見できる（`session_index.jsonl` は補助情報とし、無くても発見に支障がない）。命名規約に合わない `.jsonl` 以外のファイルは無視する
- **ソース間で ID が衝突しない。** セッション ID とキャッシュパスは「ソース ID × セッション ID」で一意になる。Claude（既定ソース）の公開 ID は従来のまま、Claude 以外のソースは `<source>:` 接頭辞付きの ID を持つ
- ログルートが存在しない環境（Codex 未使用など）ではそのソースが空の一覧を返し、エラーにしない

### やらないこと（後続 Issue）

- Codex ログの正規化・画面表示・コスト計算 — #29 / #30 / #31。**#28 では Codex ソースを production のアプリ構成に登録しない**（発見ロジックとテストまで。中身を Claude 用パーサで解釈すると全行 unknown の壊れたセッションが集計へ漏れるため、正規化が入る #29 以降で登録する）
- LiveHub（ファイル監視）の複数ルート対応 — #31
- API エンドポイントの追加・変更（本 Issue はサーバ内部の構造変更のみ）
- `npm run report`（実ログ照合）は独自走査の Claude 専用ツールのまま変更しない

### オーナー確認方法

- `npm run verify` が green（既存テストは**無変更**のまま通る = Claude 挙動不変の根拠）
- Codex セッション発見のユニットテストが green（日付階層の探索・`session_index.jsonl` 欠落時・空ディレクトリ・命名規約外ファイルの無視）
- `npm run report` の数値が本 Issue の前後で一致する

## worktree セッションの本体プロジェクトへの統合（Issue #41）

### ゴール

Claude Code を git worktree 内で起動したセッションが、ダッシュボード上で worktree 元の本体リポジトリと**同一プロジェクトとして見える**ようにする。現状は `~/.claude/projects/<エンコード済み cwd>/` のディレクトリ名ごとに別プロジェクト扱いになり、同じリポジトリの作業が worktree の数だけバラバラに表示される。

### できること

- **worktree セッションが本体プロジェクトに統合される。** cwd が git worktree 内のセッションは、worktree 元の本体リポジトリのプロジェクトとして一覧・集計に現れる（プロジェクト一覧の行数が減り、本体プロジェクトのセッション数・トークン・コストに worktree 分が合算される）
- **判定は git の正式な仕組みで行う。** エンコード済みディレクトリ名の文字列一致ではなく、cwd から上へ `.git` を探し、worktree の `.git` ファイル（`gitdir:` 行）→ 管理ディレクトリの `commondir` を辿って本体リポジトリのルートへ正規化する
- **worktree が削除された後も統合は維持される。** cwd が実在しない場合は、実在する最も近い祖先ディレクトリから上へ `.git` を探して本体を特定する（Claude Code の worktree は常に本体配下 `<本体>/.claude/worktrees/<名前>` に作られるため、削除後も祖先に本体の `.git` が残っている）。この方式はキャッシュ等の永続状態に依存しない
- **統合後のプロジェクト ID は本体の従来 ID のまま。** 本体リポジトリの既存プロジェクト（エンコード済みディレクトリ名）に合流する。本体のセッションが 1 件も無く worktree セッションだけの場合も、正規化した本体パスから同形式の ID を合成して同じ見え方にする
- **統合しても情報は落ちない。** 各セッションがどの worktree のものかは保持され、プロジェクト詳細で識別できる（表示は SPEC-DASH 側）

### やらないこと・制限

- **本体リポジトリの外に作られた worktree**（`git worktree add ../foo` 等）が削除された場合は、辿る手がかりが物理的に消えるため統合できず、従来どおり別プロジェクトとして表示する（フォールバック）
- 統合により消える旧 worktree プロジェクト ID への API・画面アクセスは **404** とする（リダイレクトはしない）
- Codex ソースは対象外（グループが日付単位で cwd ベースではないため、現状のまま）

### オーナー確認方法

1. worktree 内で起動したセッションを含む実ログでサーバを起動し、プロジェクト一覧で worktree のプロジェクト行が消え、本体プロジェクトに統合されていることを確認する
2. 本体プロジェクトのセッション数・トークン・コストが統合前の「本体 + 各 worktree」の合計と一致することを確認する
3. `npm run report` の全体集計（総トークン・総コスト）が統合の前後で変わらないことを確認する（統合は見せ方の変更であり、集計値を変えない）

## 同一プロジェクトの Claude / Codex 表示統合（Issue #49）

### ゴール

同一の本体ルートディレクトリで複数のコーディングエージェント（Claude Code / Codex）を使っている場合、ダッシュボード上で **1 つのプロジェクトとして見える**ようにする。現状は同じディレクトリの作業が Claude のプロジェクトと Codex のプロジェクト（`codex:` 接頭辞付き id）の 2 行に分かれて表示される。

### できること

- **統合は表示統合とする。** 内部データはソース別グループのまま維持する（「1 グループ 1 ソース」のデータモデル・キャッシュ・インデックスは変えない）。API・画面に出る手前で、同一の本体ルートを持つ Claude / Codex のグループを 1 つのプロジェクトにまとめて見せる
- **統合の判定はパス由来 id の一致で行う。** worktree 統合（#41 / #45）で確定した本体ルートのパス縮約（非英数字を `-` に置換した形）が同じグループを同一プロジェクトとみなす。Claude の既存プロジェクト id はこの縮約と同値であることを実測で確認済み
- **統合プロジェクトの id は接頭辞なしのパス縮約とする**（ソース中立のパス由来 id）。Claude 既存 id と同値のため、**既存の Claude プロジェクト URL はそのまま使える**
- **Codex グループの公開 id も接頭辞なしになる**（同じルートに Claude グループが無い場合も同様）。`codex:` 接頭辞付きの旧プロジェクト URL / API は **404** とする（リダイレクトはしない）
- **cwd を持たない Codex の日付フォールバックグループ（`YYYY-MM-DD`）は従来どおり**単独のプロジェクトとして表示する（パス由来 id を持たないため統合対象外）

### やらないこと・制限

- データモデル・キャッシュのソース統合（内部はソース別のまま。将来ソースを外す・足すときに他ソースへ影響しない構造を保つ）
- ソースをまたぐ worktree 併合の変更（worktree → 本体の併合は従来どおりソース内で解決し、その後の見せ方だけを統合する）
- セッション id の規約変更（Codex セッション id の `codex:` 接頭辞は従来どおり）

### オーナー確認方法

1. Claude と Codex の両方で作業した実プロジェクトが、プロジェクト一覧で 1 行に統合されて表示されることを確認する
2. 統合プロジェクトの URL が従来の Claude プロジェクト URL と同じであること、`codex:` 付きの旧 URL が 404 になることを確認する
3. `npm run report` の全体集計（総トークン・総コスト）が統合の前後で変わらないことを確認する（統合は見せ方の変更であり、集計値を変えない）

## 実測値照合レポート（`npm run report`・Issue #4）

インデクサとコスト計算の正しさを、**実ログに対する数値レポート**で機械的に検証する。

- 実ログ（`~/.claude/projects/**/*.jsonl`）全体を走査し、以下を出力する
  - レコード型分布（type / kind 別の件数）
  - ツール別呼び出し回数
  - モデル別トークン合計（input / output / cache read / cache write）
  - モデル別・全体の推定コスト（未知モデルの一覧つき）
- **事前調査時の期待値と照合し、合致しなければ非ゼロ終了する。** 実ログは追記で増え続けるため件数の厳密一致では判定せず、規模に依存しない指標で判定する
  - モデル別の実効レート（推定コスト ÷ 総トークン）が事前調査時点の値の **±10% 以内**にあること
  - 集計の内訳（input / output / cache read / cache write）の和が合計と一致すること
- **未知 type・未知モデルは警告表示に留め、合否判定には使わない。** これらは Claude Code や Anthropic 側のアップデート（新レコード type・新モデル）でも増えるため、ゲートにすると無関係な commit が止まる。レポートに目立つ警告を出して気づけるようにする
- レコード型分布・ツール分布・件数・処理時間は**表示のみ**とし、合否判定には使わない（ログの増減で変わるため）
- 最大サイズのセッションについて、初回インデックス構築とキャッシュ再利用それぞれの所要時間を計測して出力する
- レポートは `reports/`（gitignore 済み）に書き出し、リポジトリにコミットしない（実ログのパスを含むため）
- `npm run verify` に組み込む。**CI では実ログが無いため実行しない**（ローカル専用の検証工程）

## オーナー確認方法

`npm run report` の出力（件数・処理時間・スキップ行数・推定コスト）を確認する。参考値（Issue #2 時点）: 15 ファイル / 131.9MB を初回 434ms・再構築 84ms、インデックス 11,003 件・破損行 0。

実装詳細・データモデル・受け入れ基準は [docs/design/CORE.md](../design/CORE.md)。
