# usage 会計・コスト（Issue #30）

## ゴール

Codex セッションのトークン使用量と推定コストが、Claude セッションと同じダッシュボード・一覧・日次チャートに**同じ集計経路で**現れるようにする。#31 までの「未集計」表示は、実際に使用量がある Codex セッションでは数値表示に置き換わる。

Codex の `token_count` は**セッション累積値**の繰り返し記録であり（同一値の重複記録あり・行ごとの合算は多重計上になる）、そのまま足せない。累積値の**増分**だけを会計する状態機械をサーバの Codex 正規化に閉じ込め、viewer・API・集計は既存の加算可能な usage をそのまま使う。

## できること

- **Codex セッションのトークン・コストが数値で出る**: セッション一覧・Overview・日次チャートに Codex 分のトークン数と推定コストが載る。集計・コスト計算・API は既存の経路のままで、Codex 固有の分岐を持たない
- **多重計上しない**: 同一累積値の重複記録・1 ターン複数回の `token_count`・resume（session_meta 再追記）をまたいだ継続があっても、合計は「累積値の最終増分の総和」と一致する。**増分解析と全再構築で完全に同じ集計になる**
- **cached input を二重課金しない**: Codex の `cached_input_tokens` は `input_tokens` の内数（実測契約）。会計では input から cached 分を除き、cached 分はキャッシュ読み取り単価で計算する
- **reasoning tokens を二重加算しない**: `reasoning_output_tokens` は `output_tokens` の内数（実測契約）。output にのみ計上し、別枠を設けない
- **モデル切替で正しく帰属する**: usage の増分は「増分が発生した時点の turn_context.model」に帰属する。モデルやプロバイダが切り替わっても、切替前の使用量が切替後のモデルに付かない。最初の turn_context より前に現れた usage はモデル不明として計上し、未知モデル警告の対象にする
- **累積値の減少（reset / compaction / resume の巻き戻り）で壊れない**: 減少を検知したら会計 epoch を切り替え、以後の増分を新しい基準から数える。減少そのものは実ログ未観測（#17 で仮説扱い）のため、検知時の計上規則は下記の承認事項で確定する
- **Codex モデルの単価に対応する**: OpenAI 公式の価格表で確認できたモデルを `server/pricing.json` に追加する。OpenAI は cached input の割引率がモデルごとに異なるため、モデル単位で cached input 単価を指定できるようにする。**確認できないモデルは推測で埋めず**、従来どおり未知モデル警告（0 円と断定しない）に回す。単価の出典は Anthropic / OpenAI の 2 本立てで表示する

## やらないこと・制限

- **チャット表示は変わらない**: usage はセッションの会計情報であり、画面のメッセージ列には現れない
- **usage の無い Codex セッションは引き続き「未集計」表示**: `token_count` が 1 行も無い（または増分が 0 の）セッションはトークン 0 のままで、既存の「0 なら未集計表示」の規約（SPEC-DASH-089）に乗る
- **キャッシュ書き込みは扱わない**: Codex の usage に cache write に相当するフィールドは未観測（#17）。現れたら unknown 扱いで、計上はしない
- **`last_token_usage` / `rate_limits` は会計に使わない**: last は重複記録で多重計上の原因になり、rate_limits は課金と無関係（#17 の契約どおり分離）

## オーナー確認方法

- サーバを起動し、Overview・セッション一覧で Codex 行にトークン数と推定コストが表示されること、日次チャートに Codex 使用日の帯が現れることを確認する
- Claude 側の集計値・コストが従来と一致していることを確認する（`npm run verify` と `npm run report` の値比較）
- 期待値の先回り: `token_count` の無い Codex セッションは引き続き「未集計」と出る。Codex セッションの recordCount は usage 増分レコードの分だけ増える。単価未確認の Codex モデルは金額 0 + 未知モデル警告で出る

## 承認事項（2026-08-10 オーナー裁定済み）

1. **累積値の減少（epoch 切替）検知時の計上規則 → 案 B を採用**。減少を検知した行では計上せず、その値を新しい基準にする（以後の増分から数える）。多重計上は構造的に起きないが、reset 直後の最初の報告 1 回分を取りこぼす（過小側に倒れる）。減少は実ログ未観測のため実測では決められず、受け入れ軸「多重計上をしない」に従い過小側へ倒す。なお棄却した案 A（減少後の累積値を基準 0 から全額計上）は、resume の巻き戻りで計上済み分を再計上するリスクがあった
2. **集計対象の意味論の変更 → 承認**。「usage を持つ assistant レコード」だった集計対象を「usage を持つレコード（kind 不問）」に広げる。Claude 側は usage が assistant にしか付かないため**数値は変わらない**（テストで担保する）。メッセージ件数（messages）のカウントは従来どおり assistant のみとし、Codex の usage 増分レコードは件数に数えない

# 会話正規化（Issue #29）

## ゴール

Codex rollout のセッションを、**viewer を一切変更せずに**既存のチャット画面で読めるようにする。Codex 固有の解釈はすべてサーバ側の正規化に閉じ込め、viewer・API・集計は既存の正規化 DTO（`IndexRecord` / `MessageBody`）だけを見る。usage・コストはこの Issue では扱わない（#30）。

## できること

- **Codex セッションがチャット表示できる**: セッション一覧に Codex の日付グループ（`YYYY-MM-DD`）が現れ、開くと user / assistant の発言が吹き出しで、reasoning が thinking 折りたたみで、ツール呼び出しが「呼び出し＋結果」の組で表示される。ツール呼び出しと結果は `call_id` で結ばれ、Claude セッションと同じ部品で描画される
- **二重表示しない**: 同じ発言が `event_msg`（UI 通知）と `response_item`（会話の正本）の両方に記録されているが、画面に出るのは 1 回だけ。正本は `response_item` 側とし、`event_msg` の複製（agent_message / agent_reasoning / user_message）は捨てる（採用根拠は詳細設計書の実測: assistant 330:330 で出現順 1:1・本文完全一致）
- **自動注入を実ユーザー入力と区別する**: AGENTS.md 本文・環境情報・プラグイン案内などの自動注入 user メッセージと developer メッセージは、Claude の attachment と同じ「補助メタ」扱いになり、チャットのメイン列・やりとり分割を汚さない。判定は本文先頭の既知パターンのみで行う（実測: 既知パターンで 73/77 の注入を判別。パターンに合わず対応も取れない残り 4 件は**安全側に倒して実ユーザー入力として表示**する — 実入力を隠す事故の方が注入が見える事故より重いため）
- **モデル名が assistant 発言に付く**: `turn_context` の model を後続の assistant 系レコードへ関連付ける（実測: モデルが必要なレコードの前に turn_context が必ず先行する。反例 0/142）。turn_context より前のレコードはモデル不明のまま表示する
- **途中終了・欠損・未知 type で落ちない**: task_complete の無いターン、output の無いツール呼び出し、壊れた JSON 行、未知 type が混ざっても正規化は例外を投げず、取れるものだけ取って表示を継続する
- **ライブ追記に追随する**: 増分更新（追記分だけの再解析）でも turn_context のモデルなどの走査文脈が失われない（文脈をインデックスキャッシュに保存して再開する）

## やらないこと・制限

- **usage・コストの集計**（#30）: `token_count` はこの Issue では読み捨てる。Codex セッションのコストは 0 ではなく「未集計」
- **UI の Codex 向け最適化**（#31）: グループ表示が日付のままで良いか等の見直しは #31
- **カウントの意味論は Claude と揃わない**: Codex は reasoning・ツール呼び出しが独立行のため、「assistant メッセージ数」は Claude の感覚より大きくなる（行単位のカウントになる）。表示への影響は無いが、ダッシュボードの件数はこの意味論で出る
- ツール実行の通知イベント（`*_end`）のうち `call_id` で正本と結ばれるものは捨てる（結果本文は正本側にあるため）。結ばれないもの（実測: mcp 30/131 等）は欠落させず独立のツール結果として表示する

## オーナー確認方法

- サーバを起動し、実際の Codex セッションをブラウザで開いて、チャットが読める・二重表示が無い・注入が本文に混ざらないことを確認する
- Claude セッションの表示・既存テストが一切変わっていないことを確認する（`npm run verify`）

実測値・データモデル・受け入れ基準は [docs/design/CODEX.md](../design/CODEX.md)。

# スキーマ調査と合成フィクスチャ（Issue #17）

## ゴール

Codex CLI のセッションログ（`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`）には公開された安定スキーマ契約が無い。後続の実装が推測ではなく**実測で確定した契約**に依存できるよう、スキーマを調査して文書化し、テストの土台になる匿名化合成フィクスチャを整備する。

この Issue は**調査・仕様書・フィクスチャまで**。ログを読み取る production コードは書かない。

## できること（この Issue の成果物）

- **行の分類表**: rollout JSONL に現れる行の種類（top-level type / payload.type）を実測で列挙し、それぞれを「会話の正本 / イベント通知 / usage / メタ情報 / 無視してよい」に分類した表が詳細設計書にある。セッション境界・ターン境界（`task_started` / `task_complete`・`turn_id` の対応範囲・completeの無い途中終了）と、並び順の正本（ファイル順か timestamp か）・相関キー（`id` / `call_id` / `turn_id`）の契約も含む
- **重複の対応表**: 同じ発言が `event_msg`（UI 通知）と `response_item`（会話の正本候補）の両方に記録される。どちらを正本として採用し、どちらを捨てるかの対応表がある。観測範囲では assistant 発言は件数が完全一致したが、件数一致だけで 1:1 を断定せず、**対応キー・本文一致・片側欠落時の優先規則**を調査項目として契約化する。user 側は AGENTS.md や環境情報の**自動注入**が混ざるため 1:1 にならない — この非対称と、role（user / assistant / developer）・content 種別（テキスト / 画像）の分類も表に含める
- **ツール呼び出しの対応表**: `function_call` / `custom_tool_call` / `tool_search_call` とそれぞれの output の `call_id` 対応、通知側イベント（`exec_command_end` / `patch_apply_end` / `mcp_tool_call_end` / `web_search_end`）との対応、output の無い途中終了・失敗の扱いを契約化する（後続 UI で同じ操作を二重表示しないための土台）
- **トークン集計の契約**: `token_count` 行の累積仕様を実測で確認した結果が、**確定した項目と未観測の項目を区別して**記録されている。cached input / reasoning が各総数の内数か、`token_count` が 1 ターンに複数回出ること、同一累積値の重複記録があり**隣接差分の単純合算では二重計上する**こと、直近値（last）の意味と usage を確定させるタイミング、`rate_limits` を usage 会計から分離すること、resume・モデル切替でのリセット有無を含む。未観測の項目（例: compaction 時の挙動、cache write 系フィールドの有無）は仮説のまま後続 Issue の検証項目として残す
- **匿名化合成フィクスチャ**: 実測で確認した形を再現した合成 JSONL が `tests/fixtures/` にある。モデル切替・途中終了（complete の無いターン）・resume（同一セッション ID の `session_meta` 複数追記・累積 usage の継続）・壊れた JSON 行・未知 type・既知 type への未知フィールド追加・未知モデル・巨大行・usage 欠落行（`info: null`）・1 ターン複数 `token_count`・同一累積値の重複記録・自動注入 user メッセージ・developer メッセージ・画像 content・改行前の不完全な末尾行を含む。常設フィクスチャの巨大行は 50KB+ とし、実測最大（2.5MB）級はテスト内生成で検証する。実ログのパス・本文・設定値は一切含めない
- **観測条件の記録**: 観測した Codex CLI バージョン・観測日・セッション発見に必要な保存領域（`sessions` 外の履歴・インデックス類・圧縮の有無。認証情報など機微な領域は調査対象にしない）が詳細設計書に記録されており、将来スキーマが変わったときに「いつ時点の契約か」を辿れる

## やらないこと

- normalize（正規化 DTO への変換）の production 実装 — #29 以降。この Issue の成果物は文書とフィクスチャとその検証テストのみ
- Codex ログの画面表示・コスト計算 — #30 / #31

## オーナー確認方法

- 詳細設計書 [docs/design/CODEX.md](../design/CODEX.md) の分類表・対応表・トークン契約・観測条件を読み、後続実装の前提として妥当か確認する
- フィクスチャが実測スキーマと整合していることを検証する vitest が green であることを確認する（`npm run verify`）
- フィクスチャに個人情報（実パス・プロンプト本文・実プロジェクト名）が含まれていないことを確認する

実測値・分類表・受け入れ基準は [docs/design/CODEX.md](../design/CODEX.md)。
