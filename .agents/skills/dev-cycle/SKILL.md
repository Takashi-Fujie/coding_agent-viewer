# 開発サイクル

前提: 対象 Issue が GitHub に存在する。オーナーゲートが 3 箇所ある（要件合意・動作確認・PR マージ）。**ゲートを跳ばして先へ進まない。**

## 1. ブランチ作成

```bash
git switch main && git pull --ff-only
git switch -c feat/<issue番号>-<slug>
```

fix の場合は `fix/<issue番号>-<slug>`。前の Issue のブランチ上で作業を始めない。

## 2. 基本仕様書反映 → 仕様書の更新内容をオーナーが確認（要件合意ゲート）

`docs/spec/<領域>.md`（人間向け）にゴール・できること・オーナー確認方法を**挙動の言葉**で書く。書いたら更新内容のレビューをユーザーに依頼し、**合意を得るまで次へ進まない**。

## 3. 詳細設計書反映

合意した基本仕様書をもとに `docs/design/<領域>.md`（AI 向け）へデータモデル・実装方針・受け入れ基準を書く。

- 受け入れ基準は `- [ ]` チェックボックス形式・`SPEC-<領域>-<3桁連番>`・1 行 1 基準の検証可能な断定文
- チェックボックスを書くのは詳細設計書のみ（基本仕様書に書くと duplicate 検出に掛かる）
- API エンドポイント表は `docs/design/API.md` に書く（apiDrift 突き合わせ対象）

## 4. 実装ループ（TDD・受け入れ基準ごと）

1. **テストを書く（Red）** — テスト名は必ず `SPEC-ID: 説明` 形式（ID の直後にコロン）:
   ```ts
   it('SPEC-COST-003: 1h キャッシュ書き込みを input 単価 x2.0 で計算する', () => { ... })
   ```
   Red であることを実行して確認してから実装に入る。
2. **実装して Green にする** — 対象基準を満たす最小の実装。ついでの改善を混ぜない。
3. **詳細設計書のチェックボックスを `- [x]` に更新する。**

### テストデータの規約

- ダミーの SPEC-ID 文字列は予約領域 **`SPEC-SAMPLE-*`** のみ使う（実仕様 ID を書くと孤児テストとして誤検出される。Issue #1 で実際に発生）
- フィクスチャは匿名化した合成 JSONL のみ。**巨大行（50KB+）・壊れた JSON 行・未知モデル行・`<synthetic>` 行**を必ず含める
- 実ログのパス・プロンプト本文・permissions 実値をテストに書かない（public リポジトリ）

## 5. 乖離チェック（commit 前ゲート）

```bash
npm run verify && npm run spec:check
```

**両方通るまで先へ進まない。** `spec:check` でずれが出たら「Spec を直す」か「実装を直す」かをユーザーに確認する（勝手にどちらかへ寄せない）。

## 6. E2E テスト（導入済み領域のみ）

Playwright は Issue #10 で導入。導入後、画面を持つ領域は E2E を実行する。未導入の間はこの工程を省略する。

## 7. オーナー動作確認（動作確認ゲート）

コードを直しただけで完了にしない。**成果物**でユーザーの確認を受ける:

- サーバ側: `npm run report` の数値・curl の実レスポンス
- 画面側: レンダリング結果・スクリーンショット

確認依頼のメッセージには**確認手段だけでなく確認事項も添える**:

1. **確認手段**: 起動済みサーバの URL（画面なら該当ページの直リンク）・実行コマンド
2. **確認事項**: 何を見て OK と判断するかのチェックリスト。**2 観点に分けて示す**
   - **ユーザー観点（機能面）**: 画面・API の挙動として何が見えれば OK か（例:「注入メッセージがメイン列に出ないこと」）
   - **システム観点（運用・保守・アーキテクチャ）**: 構造・互換性・運用への影響（例:「既存キャッシュは全再構築される」「viewer 側に Codex 分岐が無い」）
3. **期待値**: 仕様どおりだが意外に見える挙動の先回り説明（例:「コストは未集計のため $0 表示」）
4. **承認が要る判断**: 作業中に発生した既存仕様の変更・スコープ判断があれば明示して可否を仰ぐ

指摘と実測が矛盾したら、黙って作り直さず実測値を提示して真の要件を確認する。

## 8. commit → PR

- Conventional Commits、本文末尾に `Refs #<N>`
- 仕様書・設計書の変更とコードは**同じ PR** に含める
- 実測値が得られたら数値の**要約だけ**詳細設計書に記録する

```bash
git push -u origin HEAD
gh pr create --title "feat: <要約>（SPEC-<領域>）" --body "$(cat <<'EOF'
## 概要
...

## 検証
- npm run verify: pass
- npm run spec:check: 乖離なし
- オーナー動作確認: <確認した成果物>

Closes #<N>
EOF
)"
gh run watch --exit-status
```

CI が green になったら PR の URL を報告して**待つ**。

## 9. オーナーレビューとマージ（マージゲート）

**マージはオーナーがレビューして行う。** エージェントは `gh pr merge` を実行しない。修正指摘があればこのブランチで対応し、再度 CI green まで確認して報告する。

## 10. クローズと切り替え

1. オーナーのマージを確認したら、verify / spec:check / 動作確認の結果要約をコメントに添えて `gh issue close <N> --comment "..."`（PR の `Closes` で自動クローズされた場合はコメントのみ）。**コメント冒頭に `🤖 **Claude (agent)**` の行を付ける**（gh はユーザー名義で書き込むため、本人の発言と区別する）
2. **`/compact` ではなく新セッションへの切り替えを勧める。** 次 Issue の番号を含む「そのまま貼れる最初のメッセージ」を添える（例: `Issue #5 に着手します。dev-cycle スキルで進めてください`）
